# v0.9-B2.2-A: Task Mutation Routes Authorization Matrix

This document defines the capability-based authorization matrix for all write/mutation API endpoints under the Task Management module, migrating them to Authorization Service B1.

## Summary Matrix

| No. | Method & Route | Module | Required Capability | Supported Scopes | Enforcement & Validation Rules |
|-----|----------------|--------|---------------------|------------------|--------------------------------|
| 1 | `POST /api/tasks` | task | `task.create` | own, unit, unit_tree, all | Authenticated user; requires `task.create`. Validates that `organization_unit_id` and `owner_id` (and collaborators) fall within the resolved data scope (`own`, `unit`, `unit_tree`, or `all`). Prevents actor spoofing by enforcing `created_by = session.userId`. |
| 2 | `POST /api/announcements` | task | `task.create` | own, unit, unit_tree, all | Authenticated user; requires `task.create`. Validates audience recipients and author unit within data scope. |
| 3 | `PUT /api/announcements/:id` | task | `task.update` | own, unit, unit_tree, all | Authenticated user; requires `task.update`. Loads existing announcement/task, verifies ownership (`created_by === userId`) or unit scope (`organization_unit_id` within scope). Prevents updating published announcements out of scope (IDOR/Privilege escalation protection). |
| 4 | `POST /api/announcements/:id/view` | task | `task.view` | own, unit, unit_tree, all | Authenticated user; requires `task.view`. Records task viewer status for the authenticated user (cannot record for other users). |
| 5 | `POST /api/announcements/:id/acknowledge` | task | `task.view` | own, unit, unit_tree, all | Authenticated user; requires `task.view`. Records task acknowledgment status for the authenticated user. |
| 6 | `POST /api/announcements/:id/remind` | task | `task.assign` | own, unit, unit_tree, all | Authenticated user; requires `task.assign` or notification management. Verifies task/announcement is within user's data scope before sending reminders. |
| 7 | `POST /api/tasks/:taskId/attachments` | task | `task.update` (or file_evidence.upload) | own, unit, unit_tree, all | Authenticated user; requires `task.update` / attachment upload permission. Validates task access (`creator`, `owner`, `manager` within scope, or active assignee). Rejects published announcement attachment changes. |
| 8 | `DELETE /api/tasks/:taskId/attachments/:attachmentId` | task | `task.update` (or file_evidence.delete) | own, unit, unit_tree, all | Authenticated user; requires `task.update` / attachment delete permission. Validates task access and file ownership/scope. Rejects on published announcements. |

## Security Guarantees
1. **No System Role Reliance**: B1 capability checks and data scope resolution supersede all legacy `profiles.system_role` checks.
2. **Executive Restriction**: Executives possess `all` view scope but lack mutation capabilities (`task.create`, `task.update`, `task.delete`), resulting in immediate 403 on all mutation routes.
3. **Data Scope Enforcement**: Staff are restricted to `own` or unit-bound data scope; Managers are restricted to `unit` or `unit_tree` scope; attempts to assign work outside scope or spoof unit IDs return 403.
4. **IDOR & Spoofing Prevention**: Session tokens dictate actor identity (`created_by`, `owner_id` validation against scope); client payloads attempting actor/unit spoofing are rejected.
5. **Revocation Resilience**: Revoking a role or permission immediately blocks subsequent requests with 403.
